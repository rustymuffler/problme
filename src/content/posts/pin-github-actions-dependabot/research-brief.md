## The tj-actions/changed-files Incident (2025)

**What happened**: The GitHub Action `tj-actions/changed-files`, used in an estimated 23,000+ repositories, was compromised. The attacker gained access via a **compromised GitHub personal access token (PAT)** belonging to `@tj-actions-bot`, a bot account with privileged write access to the repository — this was not a Git/SHA-collision exploit, it was credential compromise. Using that access, the attacker pushed a malicious commit and then **retroactively modified/repointed the existing version tags** (e.g., `v35`, `v44`, etc.) so that all of them pointed at the malicious commit. Anyone whose workflow referenced the action by tag (the normal `uses: tj-actions/changed-files@v45` pattern) would silently pull the malicious code on their next run.

**Mechanism confirmed**: tag manipulation following credential compromise — not a compromised SHA, not a typosquat, not a malicious new release. This is precisely the mutable-pointer risk that SHA-pinning is designed to close: repos that had pinned to a specific 40-character commit SHA were **not** affected, because their `uses:` line pointed at an immutable object that the attacker's retagging could not touch.

**Payload/impact**: The malicious code (injected via a base64-encoded addition, ultimately fetching a Python script) dumped CI runner memory looking for credentials and printed them into the public build log (`stdout`), where they were visible to anyone who could view workflow run logs (public repos = visible to anyone; private repos = visible to anyone with repo read access). Exposed secret types reported across sources: AWS access keys, GitHub PATs, npm tokens, and private RSA keys.

**Timeline**: Compromise discovered/disclosed publicly around **March 14–15, 2025** (StepSecurity is credited with the initial discovery). CISA published its advisory March 18, 2025. High-risk exposure window most commonly cited: workflow runs between **March 12, 2025 00:00 UTC and March 15, 2025 12:00 UTC**.

**CVE**: **CVE-2025-30066** (tj-actions/changed-files). A related, apparently earlier/enabling compromise of **reviewdog/action-setup@v1** was tracked separately as **CVE-2025-30154** — some analyses (Palo Alto Unit 42, BleepingComputer) suggest the reviewdog compromise may have been an initial foothold that cascaded into the tj-actions compromise, though the precise causal chain between the two is described with varying confidence across sources. `[UNVERIFIED — the exact causal link between the reviewdog and tj-actions compromises]`: treat this as "likely related, mechanism of the link not fully nailed down in public reporting" rather than a settled fact if you mention it in the article.

**Would SHA-pinning have prevented it?** Yes, for any consumer that had pinned to a specific commit SHA rather than a version tag. That's the core lesson the incident is used for industry-wide, and it's explicitly the framing GitHub, Wiz, CISA, and virtually every follow-up piece use.

**Bonus, more recent, equally strong (or arguably stronger) example — Trivy/TeamPCP, March 2026**: `aquasecurity/trivy-action` and `aquasecurity/setup-trivy` were compromised when the attacker (self-identified "TeamPCP", operating with valid but compromised credentials — not a Git exploit) **force-pushed 75 of 76 version tags** (and all 7 tags on setup-trivy) to point at malicious commits, injecting an infostealer into `entrypoint.sh` that harvested runner memory, SSH keys, cloud credentials, and GitHub PATs before exfiltrating them. This happened in March 2026 — within the last few months relative to the article's July 2026 publish context — and security researchers explicitly called out SHA-pinning as the mitigation that would have prevented exposure ("Version tags can be moved to point at malicious commits, as demonstrated in this attack"). Sources: [Wiz](https://www.wiz.io/blog/trivy-compromised-teampcp-supply-chain-attack), [The Hacker News](https://thehackernews.com/2026/03/trivy-security-scanner-github-actions.html). This could be a strong *second*, more-recent example to pair with tj-actions in the article, showing this is an ongoing pattern, not a one-off from over a year ago.

## Counterarguments to Address

- **Maintenance burden** — SHA pins are unreadable and go stale; you lose the convenience of `@v4` auto-tracking minor/patch fixes. **Response**: this is exactly why the article pairs pinning with Dependabot/`package-ecosystem: "github-actions"` — the burden is delegated to automation, and Dependabot also rewrites the version comment next to the SHA so it stays human-readable.
- **False sense of security if the SHA itself is malicious at pin time** — pinning only guarantees *the same* code runs every time, not that the code was safe when you pinned it. If you pin a backdoored commit, you've just permanently pinned the backdoor. **Response**: worth an explicit caveat in the article — SHA-pinning defends against *retroactive* tampering (the tj-actions/Trivy pattern), not against auditing failures at pin time. Pair with reviewing the action's source/diff before pinning or bumping.
- **Transitive/nested action dependencies** — pinning your direct `uses:` lines doesn't help if the action you pinned itself calls other unpinned actions internally. Adan Alvarez's 100-repo audit specifically flags this as a common blind spot.
- **Lower payoff for low-stakes personal projects** — for a small personal blog/site repo with no real secrets in CI, the actual blast radius of a compromised action is arguably low, so some argue the practice matters far more for orgs with real CI secrets (cloud credentials, npm publish tokens, etc.) than for a solo hobby project. **Response** you may want to use: even a "low stakes" repo's CI often holds things worth protecting (deploy tokens, GitHub Pages permissions, PATs), and the habit/discipline argument (build it into muscle memory before you have something more sensitive to protect) is a legitimate counter-counterargument, and ties back to the Cylance anecdote about verification-by-default as a practice, not just a reaction to actual risk level.
- **Other controls arguably matter more / first** — least-privilege `permissions:` blocks, scoped `GITHUB_TOKEN`, avoiding `pull_request_target` misuse, and OIDC instead of long-lived cloud secrets are frequently cited (including by GitHub's own secure-use docs and Wiz's hardening guide) as higher-leverage or complementary controls. SHA-pinning is necessary but not sufficient on its own.
